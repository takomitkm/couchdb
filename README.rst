=================================================================
Apache CouchDB fork: directory-flush experiment, not sent upstream
=================================================================

This is a personal fork of `apache/couchdb <https://github.com/apache/couchdb>`_.
Upstream ``main`` is unchanged; the work below lives on its own branch.

**Nothing here has been, or will be, sent to Apache CouchDB as a
contribution.** The reason is the project's own contribution policy, quoted
below.

What is on the branch
=====================

Branch: ``dirsync-proposal``. The branch also carries ``dirsync-notes/``:
the pull request that was written but not sent (``PR-DRAFT.md``), the exact
base commit and verification matrix (``LEDGER.md``), how to reproduce every
check (``REPRODUCE.md``), and the raw output under ``verification/``.

It adds a directory flush where CouchDB currently changes a directory entry
without ordering that change against the disk. CouchDB fsyncs database file
contents and orders those syncs carefully (data before footer), but it never
fsyncs the **directory** the file lives in, on POSIX or on Windows.

The two consequences, in the words of the SQLite author's summary
(`forum post 903a8f22 <https://sqlite.org/forum/forumpost/903a8f2277bf773330b0cd30d624776d12f7c9e4787f3c772e1fae8bdbc1f466>`_):

* A newly created database file can be gone after a power loss, together with
  everything that was acknowledged into it. Every other CouchDB crash path
  recovers from something left on disk; this one leaves nothing.
* A deleted database can come back. ``DELETE /db`` renames the file into
  ``.delete/`` and unlinks it, and neither step is ordered against the disk, so
  the database can reappear under its original name (or as a ``.deleted.couch``
  file when ``enable_database_recovery`` is on).

Files changed (9 files, +450/-10):

* ``src/couch/priv/couch_dirsync/couch_dirsync.c`` (new): ``fsync(dirfd)`` on
  POSIX; ``CreateFileW`` + ``FILE_FLAG_BACKUP_SEMANTICS`` + ``FlushFileBuffers``
  on Windows.
* ``src/couch/src/couch_dirsync.erl`` (new): ``-on_load``; degrades to
  ``{error, enotsup}`` when the NIF is absent.
* ``src/couch/src/couch_file.erl``: ``sync_dir/1`` and ``rename/2``, wired into
  file creation, ``delete_file/4``, ``rename_file/1`` and ``delete_dir/2``.
* ``src/couch/src/couch_bt_engine.erl``: the recovery rename and both
  compaction renames.
* ``src/couch_mrview/src/couch_mrview_compactor.erl``: view compaction swap.
* ``src/couch_mrview/src/couch_mrview_util.erl``: legacy view index rename.
* ``src/couch/rebar.config.script``: port specs for the new NIF.
* ``src/couch/.gitignore``: the port compiler's ``.d`` file.
* ``src/couch/test/eunit/couch_dirsync_tests.erl`` (new): five eunit tests.

A NIF is needed rather than plain Erlang because ``file:open/2`` on a directory
succeeds but ``file:sync/1`` returns ``{error, eisdir}`` (checked on OTP 27). A
separate NIF is needed rather than adding a function to ``couch_cfile``, because
``couch_cfile:init/0`` loads its NIF only on Unix, so a Windows build would never
see the function.

Why there is no pull request
============================

``CONTRIBUTING.md``, section "Artificial Intelligence and Large Language Models
Contributions Policy", added in ``1c33ad50f`` on 2025-06-11, says::

    The CouchDB project has a long-standing focus on license compatibility, and
    appropriate attribution of source code. AI and LLMs, by their nature, are
    unable to provide the necessary assurance, that the generated material is
    compatible with the Apache 2 license, or that the material has been
    appropriately attributed to the original authors.

    Thus, it is expressly forbidden to contribute material generated by AI,
    LLMs, and similar technologies, to the CouchDB project. This includes, but
    is not limited to, source code, documentation, commit messages, or any other
    areas of the project.

This patch was written with AI assistance, so it falls under that prohibition.
Disclosure does not lift a prohibition, and opening a pull request would mean
submitting it anyway. That is why it stays here.

If a CouchDB committer ever decides this is worth doing, the analysis and the
reproduction steps are the useful part. The code is not offered as a
contribution, and the project is free to implement it however it likes.

What was verified locally
=========================

* ``strace``, file creation: ``openat(O_CREAT)`` then ``openat(dir)`` then
  ``fsync(dirfd)``.
* ``strace``, database delete: ``rename`` into ``.delete/``, then ``fsync``
  twice, then ``unlink``.
* Windows (NTFS, non-administrator, portable OTP 27.3.4, NIF built from this
  branch): existing directory ``ok``; missing directory ``{error,enoent}``;
  directory after creating a file ``ok``; forward-slash path ``ok``; binary and
  iolist paths ``ok``; non-path argument ``{error,badarg}``.
* ``make eunit`` for the new module: five tests passing.
* ``dev/format_check.py`` (erlfmt 1.8.0, the version ``configure`` pins): passes.
* rebar's port compiler produces ``src/couch/priv/couch_dirsync.so``.

Official CI was **not** run. CouchDB's required check is ASF Jenkins
(``continuous-integration/jenkins/pr-merge``, see ``.asf.yaml``), and it only
runs for pull requests against ``apache/couchdb``. There are no GitHub Actions
workflows in the tree, so nothing runs on a fork.

Windows: capability, filesystem behaviour, contract
===================================================

Three different things that the folklore tends to merge:

* **Capability**: ``CreateFileW(dir, GENERIC_WRITE, ..., FILE_FLAG_BACKUP_SEMANTICS)``
  followed by ``FlushFileBuffers()`` works without administrator rights
  (verified on real Windows).
* **Filesystem behaviour**: MS-FSA section 2.1.5.7 note ``<80>`` states that
  flushing a directory handle "ensures that the directory structure is persisted
  to stable storage". That is a specification for filesystem implementations,
  not an application contract.
* **Contract**: no published Win32 contract says that flushing a directory
  handle persists the namespace entry. This patch therefore logs and swallows
  failures instead of failing operations: the database stays correct, only the
  durability of the entry is lost.

POSIX has the same caveat, less sharply: ``fsync(2)`` states that the directory
entry needs an explicit ``fsync()`` on the directory, and some filesystems still
cannot provide it.
